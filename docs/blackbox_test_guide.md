## 一、软件简介

**调货助手** 是一款面向 IT 硬件经销商（主要是笔记本电脑）的桌面端业务管理工具。

### 目标用户
- 笔记本电脑批发商/经销商
- 负责上游进货、下游报价、出库、收款、对账的业务人员

### 核心功能
1. **机型管理**：维护机型库（系列、CPU、内存、硬盘、显卡、屏幕、备注）
2. **批次库存**：记录每批进货的购入价、数量、剩余、入库日期、上游供应商、SN 序列号
3. **客户管理**：维护下游客户信息（名称、微信、QQ、电话），查看购买历史
4. **上游管理**：维护供应商信息，查看采购历史，管理欠款余额
5. **报价流程**：选机型 → 选批次 → 报价 → 出库 → 收款（全流程闭环）
6. **账款管理**：应收/应付汇总、收付款流水、批量收款/付款分配
7. **数据工具**：Word 价格表导入、报价单图片生成、Excel/JSON 导出、月度报告等

### 技术栈
- Python 3.11 + PyQt6 + SQLite
- 数据存储：本地 SQLite（`data/diaohuo.db`）
- 打包：PyInstaller

## 二、业务流程与状态流转

### 报价状态机

```
待确认 → 已报价 → 已出库 → 已收款
  │        │         │         │
  └────────┴─────────┴─────────┘
         均可取消（变为"已取消"）
```

| 状态 | 含义 |
|------|------|
| 待确认 | 刚创建，还没正式报价给客户 |
| 已报价 | 已正式报价，等待客户确认 |
| 已出库 | 货已发出，等待收款 |
| 已收款 | 钱已收齐，订单完成 |
| 已取消 | 订单作废 |

### 核心业务流程

```
[上游进货]                    [下游销售]
    │                              │
    ▼                              ▼
添加机型 → 添加批次(含SN)    创建报价(选批次)
    │                              │
    ▼                              ▼
batches.remaining += N         状态: 待确认
batches.sn_list = SN集合        │
    │                    客户确认 → 状态: 已报价
    ▼                              │
供应商.balance += 进货总额      出库 → 状态: 已出库
                                batches.remaining -= N
                                quotes.sn_list = 出库SN
                                │
                                收款 → received_amount += amount
                                收满 → paid="是", status="已收款"
```

### 关键数据实体关系

```
products (1) ───< batches (N) ───< quotes (N)
                     │                │
                     ▼                ▼
                suppliers         customers
                     │                │
                     ▼                ▼
                suppliers.balance  quotes.received_amount
                     │                │
                     └──────┬─────────┘
                            ▼
                      payments (收付款流水)
```

## 三、测试重点（按优先级）

### 🔴 P0 - 数据一致性（最关键）

这是本系统最脆弱的部分，**任何状态变更都必须验证关联数据是否同步更新**。

| 测试场景 | 验证要点 |
|----------|----------|
| 出库后取消订单 | `batches.remaining` 是否回补？`quotes.sn_list` 是否清空？批次SN是否不变？ |
| 删除已出库报价 | `batches.remaining` 是否回补？关联 payments 是否级联删除？ |
| 删除批次 | 关联的 quotes 和 payments 是否级联删除？供应商 `balance` 是否回滚？ |
| 删除机型 | 级联的 batches/quotes/payments 是否删除？各批次供应商欠款是否回滚？ |
| 全额收款 | `quotes.paid` 是否变为"是"？`status` 是否变为"已收款"？ |
| 部分收款 | `quotes.paid` 应为"否"，`status` 应保持原状态 |
| 修改收款金额 | `received_amount` 是否正确？`paid` 和 `status` 是否同步更新？ |
| 删除收款记录 | `received_amount` 是否回退？`paid` 和 `status` 是否同步更新？ |
| 批量收款 | 多笔订单分配收款时，是否全部成功或全部失败（原子性）？ |
| 出库SN管理 | 出库时 SN 是否正确保存到 `quotes.sn_list`？批次SN是否不被修改？ |

### 🟡 P1 - 业务流程完整性

| 测试场景 | 验证要点 |
|----------|----------|
| 完整正向流程 | 入库 → 报价 → 出库 → 收款，每一步数据是否正确 |
| 取消不同状态的订单 | 待确认/已报价/已出库，取消后各表数据变化是否符合预期 |
| 客户对账单 | 客户欠款计算是否准确 |
| 供应商对账单 | 供应商欠款计算是否准确 |

### 🟢 P2 - 边界情况

| 测试场景 | 验证要点 |
|----------|----------|
| 出库数量 > 库存剩余 | 是否被拒绝？ |
| 收款金额 > 订单总额 | 是否允许？`received_amount` 是否会超额？ |
| 无SN出库 | `quotes.sn_list` 是否为空字符串？ |
| 空备注/空方法 | 数据库是否允许空值？UI是否处理？ |

## 四、已修复但需重点回归的问题

以下问题在 v1.08 中已修复，**测试时必须重点验证，防止回归**：

### Issue #001 - 出库SN保存位置错误（已修）
- **原Bug**：出库SN被追加到 `batches.sn_list`，未保存到 `quotes.sn_list`
- **修复后**：出库SN保存到 `quotes.sn_list`，`batches.sn_list` 保持入库时的SN不变
- **测试点**：出库后查 `quotes.sn_list` 和 `batches.sn_list`，确认分开管理

### Issue #002 - paid字段更新慢一拍（已修）
- **原Bug**：`add_payment` 中 `paid` 用 UPDATE 前的旧值判断
- **修复后**：拆分为两次UPDATE，先更新 `received_amount`，再查新值更新 `paid` 和 `status`
- **测试点**：首次全额收款后，`paid` 应立即变为"是"

### Issue #003 - 删除批次不回滚供应商欠款（已修）
- **原Bug**：`delete_batch` 只删数据，不减供应商 `balance`
- **修复后**：删除前计算批次总额，从供应商 `balance` 中扣除
- **测试点**：删除批次前后查供应商 `balance`

### Issue #004 - 批量收款无事务保护（已修）
- **原Bug**：循环调用 `add_payment`，每笔独立事务，中间失败会导致部分成功
- **修复后**：新增 `_add_payment_raw` 内部函数，批量收款共用同一连接统一 commit
- **测试点**：多笔收款分配，验证原子性

### Issue #005-009 - 状态回退逻辑（已修）
- **原Bug**：收款减少/删除后，状态直接回退为"已出库"，未考虑是否真的出过库
- **修复后**：根据 `sn_list` 判断——有SN则"已出库"，无SN则"待确认"
- **测试点**：未出库的订单收款后删除，状态应回退为"待确认"而非"已出库"

## 四b、OPT 优化项测试要点（第二轮新增）

以下优化在 v1.08 之后实施，测试Agent需重点验证：

### OPT-001 - 状态机守卫（新增）
- **改动**：`update_quote_status` 新增状态流转校验，非法跳转返回 `(False, 错误信息)`
- **合法流转表**：
  ```
  待确认 → [已报价, 已取消]
  已报价 → [已出库, 已取消]
  已出库 → [已收款, 已取消]
  已收款 → []（不可变更）
  已取消 → []（不可变更）
  ```
- **测试点**：
  - 非法跳转（如 待确认→已收款）应返回 `(False, msg)`
  - 已取消/已收款 的报价不能再被修改
  - 合法跳转正常工作

### OPT-002 - 出库逻辑封装（新增）
- **改动**：新增 `ship_quote(quote_id, sn_list)` 函数，封装校验+扣减+保存SN+状态更新
- **UI层**：`on_ship_quote` 改为调用 `ship_quote`
- **测试点**：
  - 正常出库：库存扣减、SN保存到 `quotes.sn_list`、状态变为"已出库"
  - 库存不足：出库失败，库存不变
  - 状态不对（已出库/已取消）：出库失败
  - 不存在的报价ID：出库失败

### OPT-003 - 状态回退保留原状态（改进）
- **改动**：`_update_quote_payment_status` 改进，收款删除/减少后保持原状态
- **新逻辑**：
  - 收满 → "已收款"
  - 从"已收款"回退 → 根据 `sn_list` 判断（有SN→已出库，无SN→待确认）
  - 其他情况 → **保持当前状态不变**（不自动回退）
- **测试点**：
  - 已报价 → 部分收款 → 删除收款 → 应保持"已报价"（不是"待确认"）
  - 已出库 → 部分收款 → 删除收款 → 应保持"已出库"
  - 已出库 → 全额收款(已收款) → 修改减少 → 应回退到"已出库"

### OPT-004 - 清理 or True 调试代码（修复）
- **改动**：`_update_quote_payment_status` 去掉 `or True`，分开更新 `paid` 和 `status`
- **测试点**：paid 和 status 应只在真正需要变化时才更新

### NEW-001 - get_customer_stats 返回 0 而非 None（修复）
- **改动**：SQL 的 `SUM()` 加了 `COALESCE(..., 0)`
- **测试点**：新客户（无报价）查询统计时，`total_amount` 和 `total_profit` 应为 0，不是 None

## 七、特别提醒

1. **SN 字段理解**：`batches.sn_list` = 入库时的所有SN（固定不变）；`quotes.sn_list` = 本次出库的SN。两者**不能混为一谈**。

2. **状态与 paid 的关系**：`status` 是业务流程状态，`paid` 是是否结清的标志。两者**应该同步但可能不同步**——比如已收满款但 status 还没更新（虽然代码已尽量避免）。

3. **供应商 balance 的含义**：正数 = 欠供应商的钱（应付），不是供应商欠你的。

4. **测试前先清空/隔离数据**：每次测试之间确保数据库状态干净，避免测试互相影响。

5. **如果发现问题**：先确认是"本次修改引入的"还是"之前就存在的"。可以通过 `git log` 查看本次修改范围，缩小排查范围。
