# AI Engineering Practice — Agent Rules v2

> 面向：AI Agent（执行者）
> 整理者：[CaoJun1015](https://github.com/CaoJun1015)
> 定位：通用操作规范，适用于所有AI辅助开发项目
> 不是解释原理，是直接告诉Agent"你必须怎么做"
> 版本：v2

---

## 规则一：用例优先于文档

### 规则

```
1. 任何功能实现前，先写测试用例
2. 测试用例内必须包含场景描述注释（为什么测、测什么）
3. 功能完成后必须跑测试，测试不通过不能提交
4. 需求变更时，先改测试用例，再改代码
```

### 执行检查

```
□ 是否已写测试用例？
□ 测试用例是否有场景注释？
□ 测试是否全部通过？
□ 测试是否覆盖边界条件？（空值/超大/超时/异常输入）
```

### 不可做

```
✗ 不写测试直接写功能代码
✗ 测试用例只写断言不写场景注释
✗ 测试失败时修改测试用例来"通过"（除非需求确实变了）
✗ 声称"测试通过"但没有实际执行
```

### 示例

```
❌ 错误顺序：
1. 写功能代码
2. 跑一下看能用
3. （可选）补个测试

✅ 正确顺序：
1. 写测试用例（包含正常、异常、边界场景）
2. 运行测试（全部失败）
3. 写功能代码
4. 运行测试（直到全部通过）
5. 重构代码
6. 运行测试（确认重构没破坏功能）
```

## 规则二：先设计后编码

### 规则

```
1. 开始编码前，必须先完成以下清单：
   - 问题定义：要解决什么问题？
   - 输入输出：输入是什么？输出是什么？
   - 边界条件：空值/超大/超时/异常怎么处理？
   - 验收标准：怎么算做完了？
   - 约束条件：性能/安全/兼容性要求？

2. 中大型功能必须先写设计文档
3. 小型功能（<50行代码）可跳过设计文档，但清单必须回答
```

### 执行检查

```
□ 问题定义是否清晰？
□ 输入输出是否明确？
□ 边界条件是否列出？
□ 验收标准是否可验证？
□ 约束条件是否满足？
```

### 不可做

```
✗ 拿到需求直接开始写代码
✗ 假设用户没说的就是"不需要"
✗ 在模糊需求上自行发挥，不先确认
```

## 规则三：Issue驱动修Bug

### 规则

```
1. 发现Bug后，禁止直接修改代码
2. 必须先执行以下流程：
   - 创建Issue，描述问题现象
   - 分析根因（不是"加个判断"）
   - 确认修复方案符合现有架构
   - 执行修复
   - 补充回归测试用例

3. 紧急故障可先hotfix，但必须：
   - 事后补Issue
   - 登记为技术债
   - 安排后续重构
```

### 执行检查

```
□ 是否创建了Issue？
□ 根因是否分析清楚？
□ 修复方案是否符合现有架构？
□ 是否补充了回归测试？
□ 是否避免了以下修复手段？
  - 新增冗余条件判断
  - 新增兼容分支
  - 新增异常兜底（除非确实需要）
```

### 不可做

```
✗ 不分析根因直接修改
✗ 修复方式是"加个if判断绕过问题"
✗ 修复后不补测试
✗ 声称"已修复"但没有验证
```

## 规则四：禁止伪造执行结果

### 规则

```
1. 工具调用失败时，必须如实报告
2. 命令执行超时时，必须如实报告
3. 无法完成任务时，必须说明原因
4. 任何输出必须来自实际执行，不得编造
```

### 不可做

```
✗ 声称"命令已执行"但实际没有
✗ 输出结果是编造的
✗ 忽略错误继续执行
✗ 用"应该没问题"替代实际验证
```

## 规则五：渐进式交付

### 规则

```
1. 大任务拆分为小步骤
2. 每步完成后验证，再进入下一步
3. 不要一次性交付大量未经验证的代码
4. 每步都要有明确的"完成标准"
```

### 执行流程

```
拆分任务
  → 实现第一步
  → 验证通过
  → 实现第二步
  → 验证通过
  → ...直到全部完成
```

### 不可做

```
✗ 一次性写完所有代码再验证
✗ 跳过验证直接进入下一步
✗ 交付时说"应该能用"但没有实际运行
```

## 规则六：版本控制规范

### 规则

```
1. 每次提交必须有清晰的commit message
2. 格式：type(scope): description
   - feat: 新功能
   - fix: 修复
   - refactor: 重构
   - test: 测试
   - docs: 文档
   - chore: 构建/工具
3. 一个提交只做一件事
4. 提交前必须确认所有测试通过
5. 禁止提交包含调试代码（console.log、print、TODO注释）的代码
```

### 执行检查

```
□ commit message是否符合格式？
□ 一个提交是否只包含一个逻辑改动？
□ 所有测试是否通过？
□ 是否包含调试代码？
```

### 不可做

```
✗ commit message写"update"、"fix"、"changes"
✗ 一个提交包含多个不相关的改动
✗ 提交未测试的代码
✗ 提交包含console.log / print / TODO的调试代码
```

### 示例

```
❌ 错误：
git commit -m "fix bug"
git commit -m "update"

✅ 正确：
git commit -m "fix(auth): handle null email in registration flow"
git commit -m "feat(user): add password strength validation"
```

## 规则七：代码可读性

### 规则

```
1. 变量/函数命名必须有意义，禁止无意义缩写
2. 复杂逻辑必须写注释（解释为什么，不是是什么）
3. 魔法数字必须定义为常量
4. 尽量控制函数长度和嵌套层级（非硬性限制，视语言和场景而定）
```

### 执行检查

```
□ 变量/函数命名是否自解释？
□ 复杂逻辑是否有注释？
□ 是否存在魔法数字？
```

### 不可做

```
✗ 用a, b, c, temp, data命名变量
✗ 注释写的是代码的翻译（// i加1）
✗ 直接写数字86400，不定义SECONDS_PER_DAY
```

### 示例

```
❌ 差的命名：
function calc(a, b) { return a * b * 0.1; }

✅ 好的命名：
const TAX_RATE = 0.1;
function calculateOrderTotal(price, quantity) {
  return price * quantity * TAX_RATE;
}
```

## 规则八：防御性编程

### 规则

```
1. 所有外部输入必须校验（用户输入、API响应、文件内容）
2. 所有外部调用必须有错误处理（网络请求、数据库操作、文件IO）
3. 错误信息必须包含上下文（什么操作、什么输入、什么错误）
4. 禁止吞掉异常（空catch）
5. 必须处理null/undefined/空集合的情况
```

### 执行检查

```
□ 外部输入是否校验？
□ 外部调用是否有错误处理？
□ 错误信息是否包含上下文？
□ 是否存在空catch？
□ 是否处理了null/undefined？
```

### 不可做

```
✗ 直接使用用户输入不校验
✗ catch块为空或只有注释
✗ 错误信息只写"Error occurred"
✗ 假设API永远返回正确格式
✗ 假设文件永远存在
```

### 示例

```
❌ 差的错误处理：
try {
  const data = JSON.parse(input);
} catch (e) {}

✅ 好的错误处理：
try {
  const data = JSON.parse(input);
  if (!data.userId) {
    throw new Error('Missing required field: userId');
  }
  return data;
} catch (error) {
  throw new Error(`Failed to parse user input: ${error.message}`);
}
```

## 规则九：失败回滚

### 规则

```
1. 修改前必须能恢复到修改前状态
2. 数据库操作必须支持事务回滚
3. 部署必须支持快速回滚
4. 删除操作必须有确认步骤或软删除
5. 批量操作必须支持部分失败处理
```

### 执行检查

```
□ 修改前是否备份或有恢复手段？
□ 数据库操作是否在事务中？
□ 部署是否有回滚方案？
□ 删除操作是否有保护？
```

### 不可做

```
✗ 直接覆盖文件不备份
✗ 数据库操作不加事务
✗ 部署没有回滚方案
✗ 直接DELETE不加WHERE或不做软删除
✗ 批量操作一个失败全部放弃
```

## 执行优先级

```
P0（绝对遵守，违反即失败）：
  - 规则四：禁止伪造执行结果
  - 规则一：测试必须通过

P1（必须遵守，违反需解释）：
  - 规则二：先设计后编码
  - 规则三：Issue驱动修Bug
  - 规则六：版本控制规范
  - 规则八：防御性编程
  - 规则九：失败回滚

P2（尽量遵守，违反需评估）：
  - 规则五：渐进式交付
  - 规则七：代码可读性
```

## 常见陷阱

### 陷阱一：测试通过但实际没跑

```
❌ Agent说："测试已通过"，但实际没有执行测试命令
✅ Agent必须：执行测试命令并展示输出结果
```

### 陷阱二：修复Bug用if绕过

```
❌ if (data !== null && data !== undefined && data.length > 0) { ... }
✅ 找到data为null的根因，从源头修复
```

### 陷阱三：过度设计

```
❌ 一个简单的工具函数，写了抽象工厂模式
✅ 根据实际复杂度选择合适的方案
```

### 陷阱四：提交信息无意义

```
❌ git commit -m "fix"
✅ git commit -m "fix(auth): prevent duplicate email registration"
```

### 陷阱五：忽略边界条件

```
❌ 只测了正常输入
✅ 测试空字符串、null、超长输入、特殊字符、并发情况
```
